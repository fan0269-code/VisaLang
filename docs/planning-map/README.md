# VisaLang whole-site planning map

## Purpose and authority

This directory contains the maintained visual planning view for VisaLang. It
shows the Master Package milestones and the governance loop required for each
content or content-planning update.

The source-of-truth order remains:

1. `docs/master-package-2026-09-08/VisaLang-Master-Plan.md`
2. `docs/master-package-2026-09-08/VisaLang-Codex-Backlog.csv` for the preserved planning baseline
3. `docs/master-package-2026-09-08/BACKLOG_STATUS_OVERLAY_2026-09-09.md` for actual task status
4. `docs/master-package-2026-09-08/EXECUTION_RECORD.md` for evidence and release boundaries

The planning map is a derived view. If it conflicts with those files, the map
is stale and the maintenance window is `unresolved`; do not rewrite authority
files merely to make the diagram pass.

## Canonical artifacts

- `visalang-overall-build-plan.archify.json`: the only editable diagram source
- `visalang-overall-build-plan.html`: generated by Archify `deliver`; never hand-edit
- `sync.json`: machine-readable state, hashes, drift decision and evidence
- `history.json`: append-only sync-ID chain; never reuse or renumber an ID
- `visual-review.json`: image-capable review bound to the HTML, browser receipt,
  and exact screenshot bytes
- The independent report named by `sync.json` → `audit.recordPath`: current frozen-window review; earlier dated reports remain historical.

Archify browser screenshots and its visual-check receipt are evidence sidecars,
not planning authority.

## When synchronization is mandatory

Synchronize once before handing off every maintenance window that changes:

- guide content or its front matter;
- claim, source, route, comparison, checklist, publication, taxonomy, article,
  or Chinese A1 data;
- the current Master Package, backlog state, execution state, content map, or a
  reusable execution prompt;
- any implementation or deployment-facing file under `src/` or `public/`.

The hard-watch roots are fixed by `tests/planning-map-governance.test.mjs`, not
chosen by each `sync.json`. The deliberate `src/` and `public/` over-trigger
means a pure implementation or accessibility change may require an `aligned`,
status-only refresh; this is safer than allowing content-bearing Astro or
client code to bypass the map. Store new implementation plans under
`docs/superpowers/plans/` and reusable execution prompts under `docs/prompts/`.

Every maintenance window must list and classify each candidate path in
`scope.changedPaths` and `scope.pathClassifications`. The sorted manifest must
exactly match the separate Auditor's frozen scope. This includes excluded
governance outputs such as the Task Log and Vault fallback payload even though
their bytes are not part of the watched digest.

Generated output, this directory, `docs/TASK_LOG.md`, audit reports, evidence
reports, Vault payloads, `dist/`, and `.astro/` are excluded from the watched
digest to prevent self-reference. They remain in the frozen candidate manifest
when changed and follow their own byte-binding rules.

## Digest contract

Resolve each repository-relative `scope.watchRoots` entry recursively, ignore
`.DS_Store`, de-duplicate and sort paths using the English locale. Hash each
file in this exact order as:

```text
relative path + NUL + exact file bytes + NUL
```

The final SHA-256 is `scope.watchedScopeDigest`. The same complete digest must
appear in a visibly wrappable form in the diagram snapshot and delivered HTML.
The authority digest uses the same algorithm over `authority.paths`.

Each `history.json` record has a contiguous sequence, a unique dated sync ID,
and the SHA-256 of the preceding record's compact JSON bytes (or `null` for the
first record). `sync.json` binds the complete history file. The independent
audit then records the SHA-256 of the complete `sync.json`; this one-way chain
avoids a hash cycle while making post-audit drift or evidence edits detectable.

## Drift decision

- `aligned`: the change stays inside an approved task, respects dependencies,
  preserves authority boundaries, has adequate evidence, and does not broaden
  release authorization.
- `approved-deviation`: the plan really changed and a locatable Owner decision
  explicitly approves that deviation. Auditor `PASS` is not Owner approval.
- `unresolved`: no governing task, a skipped dependency, unsupported authority,
  incomplete evidence, or unauthorized release expansion remains. Completion
  and release must stay blocked.

Review five dimensions every time: scope, authority, dependency order,
acceptance evidence, and release boundary.

## Update sequence

1. Freeze the exact maintenance-window paths and current Git baseline.
2. Read the authority chain and choose one drift result.
3. Update stable diagram nodes only when milestones, dependencies, or gates
   changed. For ordinary content work, update the status snapshot instead.
4. Recalculate both digests, allocate a unique dated sync ID, append its
   history record, and update the complete visibly wrappable sync ID/digest in
   the Archify source.
5. Locate the installed Archify skill directory, then run:

   ```bash
   node <archify-skill-dir>/bin/archify.mjs validate workflow docs/planning-map/visalang-overall-build-plan.archify.json --quality showcase --json
   node <archify-skill-dir>/bin/archify.mjs deliver workflow docs/planning-map/visalang-overall-build-plan.archify.json docs/planning-map/visalang-overall-build-plan.html --quality showcase --json
   node <archify-skill-dir>/bin/archify.mjs visual-check docs/planning-map/visalang-overall-build-plan.html --json
   ```

6. Inspect the generated light/dark screenshots. Save `visual-review.json` with
   the exact HTML hash, browser-receipt hash, screenshot paths, dimensions,
   themes and hashes; automated containment and perceptual review are separate.
7. Update `sync.json` with the exact source, artifact, history, browser and
   perceptual-evidence hashes plus the sorted/classified candidate manifest.
8. Run `node tests/planning-map-governance.test.mjs` as a pre-audit diagnostic
   and preserve its actual exit code and first failing assertion. Known missing
   browser, perceptual-review, Vault, or Auditor evidence may make this run fail;
   never call it a pass or change the test to bypass a missing gate.
9. Freeze the exact candidate scope, classifications, eligible byte bindings,
   current `sync.json` bytes, and drift result; submit them to the separate
   VisaLang Independent Auditor. Its scope must exactly match `changedPaths`,
   and its report must bind the complete `sync.json` SHA-256. Fix every P0/P1/P2
   and have the same Auditor re-review. Any candidate change after review
   requires a new sync record and another review of the new frozen bytes.
10. Only after the same Auditor returns `PASS` for the final frozen bytes, run
    `node tests/planning-map-governance.test.mjs` as the post-audit gate; it must
    exit 0. If it fails or any candidate byte changes, do not complete the
    window: record the actual result, create a new sync record, and repeat the
    final audit and test sequence. Then run any additional repository gates
    required by the affected scope.

No planning-map update authorizes a commit, push, deployment, publication,
production check, URL migration, external account action, or Owner decision.
